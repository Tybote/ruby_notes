====== REST & ActionPack ======

REST is a set of good principles to build good Web applications.
REST is all about resources.

A Web applicaiton is called RESTful if it offers these 7 actions :

1. List available resources
2. Show a specific resource
3. Destroy an existing resource
4. Provide a way to create a resource
5. Create a new resource
6. Provide a way to update a resource
7. Update an existing resource

Action Pack is a way to get Controller and View to work together to let us interact with
resources in the Model layer (CRUD operations).

This command does generate all we need to use RESTful operations automatically
and see directly the results in views :

Example of blog posts :

rails g scaffold posts title content:text

We can use the command : "rake routes" to show the different routes we generate,
according to RESTful actions.

Useful helpers :

"respond_to" (see destroy action) : specifies how to respond to a request with a specified format.
Takes an optional block which specified the format : ex : html, json, xml, etc
The block specifies how to handle each format.
Ex :
def destroy
  @post.destroy
  respond_to do |format|
    format.html { redirect_to posts_url, notice: 'Post was successfully destroyed.' }
    format.json { head :no_content }
  end
end

"redirect_to" (see the example above) : send a respond to a browser to redirect somewhere else.
Can take a full url as parameter, or a named route.


Strong parameters :
Allows only specified parameters, for example to create a new item.
For example with the create method :
def create
  @post = Post.new(post_params)
....

AND

# Never trust parameters from the scary internet, only allow the white list through.
def post_params
  params.require(:post).permit(:title, :content)
end

Flash parameters :
flash persists for exactly one request after the current request/response cycle.
Generally used for notify success or fail of a specified action.
For example, the notice option is a flash parameter in the Create action.
We could have "alert" instead of "notice" to notify a fail.
Also, the basic syntax is : flash[:attribute] = value

Examples :

def create
  @post = Post.new(post_params)

  respond_to do |format|
    if @post.save
      format.html { redirect_to @post, notice: 'Post was successfully created.' }

....

def destroy
   session.delete(:current_user_id)
   flash[:notice] = "You have successfully logged out."
   redirect_to root_url
 end

....

redirect_to root_url, notice: "You have successfully logged out."
redirect_to root_url, alert: "You're stuck here!"
redirect_to root_url, flash: { referral_code: 1234 }

Partial :
partial is just a snippet of reusable template, almost like a fragment,
that has an underscore in its name, or a file name. So it's _form for example,
and it accepts parameters that are available to you when the template is rendered : <%= render 'form' %>


Helper "form_for" : generates a form tag for passed in object.
Uses "POST" by defaults unlike classical html forms.

f.text_field : generates input type "text" fiedl.
f.text_area : generates a larger area to write text content. Can specify a size.
Many other helpers : f.date_select, f.time_select, etc.
:placeholder : hash entry to specify a gray text in a text field(placeholder, go google trad)

f.submit : accepts a name of the button with the first parameter, or generates one based
on the model and type of action : Create, Update, etc.
Examples:

<div class="field">
  <%= f.label :title, "Heading" %><br>
  <%= f.text_field :title, placeholder: "Have a great title?" %>
</div>

<div class="field">
  <%= f.label :content %><br>
  <%= f.text_area :content, size: "10x3" %> (10 columns and 3 rows)
</div>

LAYOUTS :
 1. views/layouts/application.html.erb is used by default as a shell by any view template.
 2. if a layout with a controller name is present in the layouts folder, it will be applied.
 3. we can use layout method inside a controller to specify the controller layout : layout 'some_layout'
 4. or we can specify a layout for only one method, with : render layout: 'my_layout'
 5. or if we don't want a layout, just use : render layout: false

=========== Nested Resources =============

We can define a nested resource in the routes.rb file.
Example of book's notes : notes are embedded within a single book:

routes.rb :

resources :books do
  resources :notes, only: [:create, :destroy]# Nested resource
end

We can allow a set of actions for a nested resource like the above : create and destroy.
Then, we just have to fill the note controller defining create and destroy actions.

The routes will look like that : We see that a note a specify after a book id.

book_notes POST   /books/:book_id/notes(.:format)     notes#create
 book_note DELETE /books/:book_id/notes/:id(.:format) notes#destroy
     books GET    /books(.:format)                    books#index
           POST   /books(.:format)                    books#create
  new_book GET    /books/new(.:format)                books#new
 edit_book GET    /books/:id/edit(.:format)           books#edit
      book GET    /books/:id(.:format)                books#show
.......

We must pass each time the parent and the child when we manipulate a nested resource
in html content to identify the paths, in form_for or link_to helpers for example.
For example with the notes of a book, in the note partial view, when we want to
delete a note from a book, note the use of the two parameters : @book and note
to specify the path.

    <%= link_to "Delete Note", [@book, note], method: :delete %>

When we wanna create a new note from a book show view, we call again the two paramers
in the form: @book and @book.notes.new to specify the path.

  <%= form_for([@book, @book.notes.new]) do |f| %>

======= Authentication =========
We will use the gem  'bcrypt' put by default in the Gemfile but commented.

To be able to authenticate a user, the user must have in his table the "password_digest" column,
it's mandatory.
Then in the model of the user, put this helper : "has_secure_password" . It adds a virtual
attribute which is "password" that we'll use for create a new user. When creating a new user
with a password attribute, the password will be "hashed" or "encrypted" and added to the
password_digest column. To identify the user, the password entry must match after
encrypting to the password_digest entry.

==== HTTP session ====

We create a session resource : rails g controller session new create destroy
We fill the session view with a form getting  reviewer attributes and redirecting to sessions#create action.

<%= form_for(:reviewer, url: sessions_path) do |f| %> <!-- sessions_path = sessions#create, see rake:routes -->

We can configure new routes to redirect to login/logout pages within routes.rb,
with the appropriate HTTP method :

resources :sessions, only: [:new, :create, :destroy]
get "/login" => "sessions#new", as: "login"
delete "/logout" => "sessions#destroy", as: "logout"

We complete the create action of the session controller to identify and valide
the user: Note the session keyword : it creates a cookie for the session in the client browser.

def create
  reviewer = Reviewer.find_by(name: params[:reviewer][:name])
  password = params[:reviewer][:password]

  if reviewer && reviewer.authenticate(password)
    session[:reviewer_id] = reviewer.id
    redirect_to root_path, notice: "Logged in successfully"
  else
    redirect_to login_path, alert: "Invalid username/password combination"
  end
end

To destroy a session, call "reset_session" :

def destroy
  reset_session # wipe out session and everything in it
  redirect_to login_path, notice: "You have been logged out"
end

To lockdown the website unless we are logged in, put a before_action in the ApplicationController :

before_action :ensure_login

protected
  def ensure_login
    redirect_to login_path unless session[:reviewer_id]
  end

We put the ensure_login action as protected to get it the chield controllers (developer's controllers).
To avoid an infinite loop with the ensure_login before_action, we put this helper in the SessionsController :
it allows to skip the before_action ensure_login for specified actions.

skip_before_action :ensure_login, only: [:new, :create]
